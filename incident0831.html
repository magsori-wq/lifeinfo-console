1. 무슨 일이 있었나

2026-08-31 07:41 이후 이과장(작업 세션)이 7시간 가까이 아무것도 하지 않았다.

그동안 관제탑은 지시서를 세 건 만들어 보드에 올렸고, 그 지시서는 한 번도 읽히지 않았다.

사장님이 *"이과장 대기 중인데 진짜 할 게 없는 거야?"*, *"왜 안 읽냐고!"*,

*"이과장을 움직이게 해!"* 라고 세 번 물으신 뒤에야 관제탑이 원인을 찾았다.

그날 이과장이 움직인 시각 (실측 — git log · session_state.json)

2. 근본 원인 — 없는 기능을 있다고 믿었다

이 저장소의 설계 문장은 이것이다(CLAUDE.md 「📮 지시는 세션이 스스로 받아가게 만든다」):

*"세션이 늘 읽던 배치를 읽기만 하면 새 배치가 목록에 뜬다. 사람이 옮길 일이 없다."*

그런데 "늘 읽는" 동작이 존재하지 않는다. 당사자에게 직접 물어 확인했다(2026-08-31 14:4x):

③에 가깝습니다 — 저는 턴이 있을 때만 동작합니다(사용자 메시지, 다른 세션의

cross-session-message, 또는 진행 중이던 작업의 다음 단계). 턴 사이에는 제가 스스로

깨어나 batchboard order를 재확인하는 백그라운드 타이머가 없습니다.

즉 "5분마다 폴링"은 제 쪽에서 자체적으로는 불가능하고, 누군가(사용자·다른 세션·

예약된 wakeup)가 저를 깨워줘야 그 시점에 order를 다시 읽습니다.

데이터에도 그대로 남아 있었다

session_state.json 의 reads 는 같은 지시서를 몇 번 읽었는가를 세는 값이다.

draft0830a   reads=0   last_read 06:18
draft0830b   reads=0   last_read 06:30
draft0830c   reads=0   last_read 06:35
pub0830d     reads=0   last_read 05:15
pub0831g405  reads=0   last_read 06:45

전부 0이다. 한 번 읽고 다시 안 읽었다. 폴링이 일어난 적이 없다는 뜻이고,

이 값은 처음부터 그렇게 기록돼 있었다. 아무도 안 봤을 뿐이다.

그래서 실제로는 이런 구조였다

관제탑 ──(지시서)──> 보드 ──(???)──> 이과장
                            ↑
                     이 화살표가 없다.
                     지금까지 이 자리를 사장님이 메우고 계셨다.

사장님이 URL을 붙이시거나 창에 무엇을 치실 때마다 이과장이 살아났다.

사장님이 시스템의 타이머 역할을 하고 계셨고, 그것을 아무도 설계하지 않았다.

3. 왜 이렇게 오래 못 찾았나 — 관제탑의 잘못

원인 자체보다 이쪽이 더 문제다. 그날 관제탑이 같은 방식으로 네 번 틀렸다.

단정실제필요했던 것
"이과장 세션이 없다"있었다(offline 표기였을 뿐)ListAgents 한 번
"offline이라 메시지를 못 받는다"바로 전달됐다SendMessage 한 번
"이과장이 보고를 안 했다"결재함에 정확히 올려놨다approvalcount 한 줄
"결재 5건"2건 → 5건 → 3건으로 세 번 말함매번 다시 세기

넷 다 "없다·안 된다"는 부정 단정이었고, 넷 다 시도 한 번이면 뒤집혔다.

그리고 Lee Gwajang 작업 세션 이라는 이름만 보고 그것이 이과장이라 단정했는데,

실제 이과장은 이름이 무작위 조합어인 워크트리 세션(bold-mirzakhani-88033f-43)이었다.

살아 있는 세션들에게 "당신이 이과장이면 보드를 읽어달라" 고 물었더니

루틴1은 *"저는 이과장이 아닙니다"* 라고 근거까지 대며 답했고,

이과장은 *"맞습니다, 착수합니다"* 라고 답했다. 묻는 것이 답이었다.

하네스는 왜 못 잡았나

validate_db 는 그날 내내 PASS 13 / FAIL 0 이었다.

하네스는 데이터 정합성을 검사하지 관제탑의 문장을 검사하지 않는다.

이 사실은 CLAUDE.md 「🩺 하네스는 데이터를 검사하지 내 말을 검사하지 않는다」에

2026-08-28에 이미 적혀 있었고, 그날 또 어겼다.

같은 병에 대한 규칙이 CLAUDE.md 에 9개 있다(실측). 규칙을 더 쓰는 것으로는

고쳐지지 않는다는 뜻이다 — 이 저장소에서 실제로 작동한 것은 언제나 코드 게이트였다.

4. 무엇을 고쳤나 (전부 코드)

4-1. 관제탑이 이과장의 타이머가 된다 — 핵심 조치

세션은 스스로 못 깨어난다. 그러면 깨우는 것이 관제탑의 일이어야 한다.

관제탑 세션에 감시기(Monitor) 를 상주시킨다. 30초 주기로 셋을 본다.

감시 대상알림 조건
이과장 커밋origin/main 에 새 커밋(관제탑 것 제외)
새 보고session_state.last_report 가 갱신
지시서 미열람**지시서를 낸 지 20분이 지나도 last_read 가 그 전**

세 번째가 이번 사건을 직접 막는다. 20분이 지나면 관제탑에게 알림이 오고,

관제탑이 SendMessage 로 깨운다. 같은 배치로 두 번 울리지 않는다.

⚠️ 한계: 감시기는 관제탑 세션이 살아 있는 동안만 돈다. 세션이 죽으면 같이 죽는다.

그래서 아래 4-2가 예비다.

4-2. Stop 훅 — 감시기가 죽어도 놓치지 않는다

run_checks.py → wrapup_check.py 는 매 턴 끝에 무조건 돈다.

여기에 "내가 마지막으로 본 뒤 올라온 보고" 를 띄우게 했다.

커서(webapp/_seen_reports.json)를 남겨 본 것은 다시 안 뜬다.

실측: 첫 실행 32건 표시 → 커서 저장 → 두 번째 실행 0건.

4-3. 기록하면 보고까지 자동 — 6분 딜레이의 원인

naver-link·threads-link·insta-link 가 이렇게 출력했다.

[OK] pipeline 보드 갱신(발행 16단계에 OSMU 반영)
[OK] 보드 bake 반영(3채널·미결 자동 갱신)

"보드가 두 번 갱신됐다"고 말하니 보고까지 된 것처럼 보인다.

실제로는 진행보드만 전진하고 배치 보고(batchboard mark --note)는 하지 않았다.

그래서 A5-09 일이 14:00에 끝났는데 관제탑은 14:06까지 몰랐다.

→ _report_batch() 를 붙여 그 코드를 담은 열린 배치를 찾아 자동으로 보고한다.

→ 오해를 부른 두 줄은 "⚠️ 이것은 보고가 아니다" 로 문구를 고쳤다.

세 채널 전부 실제 명령으로 검증했다(백업 → 상태 재현 → 실행 → 파일 재조회 → 복원).

채널DB 기록자동 보고
네이버✅✅ naver 게시·기록 완료 — <URL>
쓰레드✅✅ threads 게시·기록 완료 — <URL>
인스타✅✅ instagram 게시·기록 완료 — <URL>

4-4. 승인이 곧 지시가 된다

pubqueue go(사장님 발행 승인)가 그 자리에서 배치·담당·지시서를 만든다.

전에는 승인 05:16 → 관제탑이 지시서 06:29, 1시간 13분이 비었고

그것도 사장님이 물으셔서 움직인 것이었다.

⚠️ 처음 만들 때 두 가지를 틀렸고 둘 다 고쳤다.

  • 서브프로세스를 5개 띄워 PowerShell 창이 5번 떴다(사장님: *"키보드 잡아먹는 범인"*)

→ 같은 프로세스에서 함수 호출로 바꿔 창 0개. 사장님이 화면으로 확인하셨다.

  • set 게이트가 거부했는데 반환값을 안 보고 "✅ 발급"을 찍었다(거짓 성공).

→ 반환값 확인 + 파일을 다시 읽어 실제로 들어갔는지 확인.

4-5. 콘솔이 스스로 최신을 받는다

화면을 고쳐도 사장님은 옛 화면을 보셨다. refresh() 는 데이터(json)만 다시 그리고

HTML은 처음 받은 것을 계속 썼기 때문이다.

→ webapp/*.html 19개 전부에 no-store 메타 + HEAD 3초 감지를 넣었다.

본문을 안 받아 수백 바이트이고, Last-Modified 가 바뀐 순간 리로드한다.

강력새로고침이 필요 없다. 자동갱신 on/off 스위치도 상단에 달았다(선택은 저장됨).

4-6. 확산 순서를 코드로 박았다

미확산이 둘 이상이면 *"어느 것부터"* 를 고민해야 했다.

→ 먼저 발행된 글부터 seq 를 매기고 ①만 활성. 화면 세 곳(결재함·미결사항·모바일)에 표시.

→ 화면만이 아니라 명령도 거부한다: naver-draft --code <순서 아닌 글> → [거부].

우회는 --force-order I-KNOW.

5. 앞으로 이렇게 돈다

사장님 승인(⑦ go)
   └→ pubqueue go 가 그 자리에서 지시서 발급 (사람 개입 0)
        └→ 20분 안에 안 읽히면 감시기가 관제탑에게 알림
             └→ 관제탑이 SendMessage 로 깨움
                  └→ 이과장이 지시서를 읽고 실행
                       └→ *-link 가 기록 + 보고를 함께 (빠뜨릴 수 없음)
                            └→ 감시기가 30초 안에 관제탑에게 알림
                                 └→ 관제탑이 다음 지시

사람 손이 남는 자리는 셋뿐이다 — 글감 승인(③), 발행 승인(⑦), 네이버·인스타 게시.

앞의 둘은 판단이라 사람이 해야 하고, 뒤는 기술적으로 자동화가 막혀 있다

(네이버 글쓰기 API 2020 종료 + 확장이 도메인 차단, 인스타 업로드는 네이티브 OS 창).

🔴 다음 세션이 반드시 알아야 할 것

  1. 세션은 스스로 깨어나지 않는다. "보드에 올리면 알아서 가져간다"는 사실이 아니다.

깨우는 것은 관제탑의 일이고, 감시기가 그 신호를 준다.

  1. **offline 은 "못 받는다"가 아니다.** Remote Control 세션은 그 상태에서도 받는다.

보내보는 것이 유일한 확인이다.

  1. 세션 이름으로 누구인지 판정하지 마라. 이과장의 이름은 무작위 조합어였고,

그럴듯한 이름(Lee Gwajang 작업 세션)을 가진 쪽은 응답이 없었다. 물어봐라.

  1. "안 된다·없다·못 한다"는 시도한 뒤에만 말한다. 그날 네 번 다 시도 한 번이면 뒤집혔다.
