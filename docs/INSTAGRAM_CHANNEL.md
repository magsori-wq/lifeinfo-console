쓰레드 확산 다음에 **인스타 확산**을 파이프라인 단계로 넣고, 콘솔 전체를 3채널 →
4채널로 확장했다.

---

## ⚠️ 먼저 — 이 변경은 PC 복귀 후 로컬 원본에 다시 넣어야 한다

수정한 파일은 **배포 산출물**이다. 원본은 수리 중인 PC에 있다.

| 파일 | 성격 | 덮어써지는 시점 |
|---|---|---|
| `progress.html` | **생성물** (`window.__DATA__` + `baked_at` 이 박혀 있다) | studio 의 `bake` 실행 시 |
| `dashboard.html` | `webapp/dashboard.html` 의 배포 사본 | `deploy.bat` 실행 시 |

즉 PC가 돌아와 `bake` 나 `deploy.bat` 을 한 번 돌리면 **이 변경은 사라진다.**
아래 §3 의 내용을 로컬 원본(`studio/` 의 progress 템플릿, `webapp/dashboard.html`)에
반영해야 영구히 남는다.

## 2. 작업 중 발견한 버그 (같이 고침)

### 확산 단계가 미게시 글을 완료로 표시했다

원래 코드는 DB에서 체크를 **추가만** 하고 제거하지 않았다:

```js
if(_cur.osmu.naver && checked.indexOf(11)<0) checked.push(11);   // 추가만
```

그래서 `board_seed` 가 미리 찍어둔 낡은 `checked` 값이 그대로 살아남았다.
**실측**: `C2-07` 은 DB에 `osmu` 기록이 아예 없고 `progress.json` 메모도
"네이버·쓰레드 미게시, 인스타 소싱중" 인데, `checked` 에는 11·12·13 이 들어 있어
보드가 확산 완료로 표시했다.

단계 번호를 밀면서 이 문제가 더 커진다 — 낡은 13(옛 교차링크)이 새 13(인스타 확산)을
가리키게 되어 **의미까지 어긋난다.**

**고친 방식**: 확산 단계(11~14)는 시드값을 버리고 **DB `osmu` 에서만 도출**한다.
DB는 실제로 게시된 것의 기록이므로 확산 여부의 유일한 정답이다.

```js
const derived={11:!!om.naver,12:!!om.threads,13:!!om.instagram,14:!!(om.naver&&om.threads)};
checked=checked.filter(n=>!(n in derived));      // 시드값 무시
Object.keys(derived).forEach(k=>{if(derived[k])checked.push(+k);});
```

이제 번호가 밀려도 자동으로 맞고, 보드 데이터가 뒤처져도 실제 게시를 반영한다.

**검증 결과**

| 글 | DB osmu | 표시 |
|---|---|---|
| C2-07 | 없음 | 10/16 · 현재 **11. 네이버 확산** ← 메모와 일치 |
| A1-02 | 네이버·쓰레드 | 현재 **13. 인스타 확산** ← 다음 할 일로 지목 |
| F1-07 | 3채널 완료 | 14/16 · 현재 15. 색인 요청 |

### 미결 관리의 I 칩은 DB에서 도출해야 한다

`pending.json` 의 `ch` 는 `{g,n,t}` 만 담는다 — 생성기(`pending.py`)가 인스타를
모른다. `ch.i` 를 믿으면 **이미 게시한 글도 `I✗`** 로 나온다.
그래서 코드에서 DB를 직접 참조하게 했다:

```js
const osmuByCode={}; recs.forEach(r=>{if(r.code)osmuByCode[r.code]=r.osmu||{};});
// ...
cb((osmuByCode[a.code]||{}).instagram,'I')
```

`pending.py` 가 `ch.i` 를 내보내도록 고치면 이 우회는 지워도 된다.

### 교차링크(14) 조건에 인스타를 넣지 않은 이유

인스타는 54/153편(35%)이라 확산률이 낮다. 조건에 넣으면 **대부분의 글에서 교차링크가
미완으로 뒤집혀** 보드가 후퇴한다. 네이버·쓰레드(99%) 기준을 유지했다.
인스타 확산률이 올라가면 그때 조건에 넣는 것이 맞다.

## 3. PC 복귀 후 로컬 원본에 반영할 것

### 3-A. progress 생성 템플릿 (studio)

`bake` 가 만드는 progress 템플릿에서 아래 3곳을 고친다.

1. `STEPS` 배열 — 13번에 인스타 삽입, 이후 번호 +1
   ```js
   {n:12,who:'me',t:'쓰레드 확산',star:1},
   {n:13,who:'me',t:'인스타 확산',star:1},      // ← 추가
   {n:14,who:'ai',t:'채널 교차링크'},
   {n:15,who:'me',t:'서치콘솔 색인 요청',star:1},
   {n:16,who:'ai',t:'색인 반영 실측'}
   ```
2. 확산 단계 도출 블록 — §2 의 `derived` 방식으로 교체
3. 4채널 지표·미결 I 칩·조언 — 배포된 `progress.html` 을 그대로 참고

가장 확실한 방법: 지금 저장소의 `progress.html` 을 열어 `__DATA__` 라인만 제외하고
템플릿과 diff 하면 바뀐 부분이 그대로 보인다.

### 3-B. `webapp/dashboard.html`

저장소의 `dashboard.html` 로 교체하면 된다 (런타임에 JSON 을 fetch 하는 정적 파일이라
데이터가 박혀 있지 않다).

### 3-C. 생성기 쪽 후속 정리 (권장)

- `board_seed` — 15 → 16단계로 총 단계 수 갱신. 확산 단계(11~14)는 이제 보드가
  DB에서 도출하므로 **시드에 찍지 않는 것이 맞다** (찍어도 무시되지만 혼란을 준다).
- `pending.py` — `ch` 에 `i` 추가. 그러면 §2 의 DB 우회를 지울 수 있다.
- `selfcheck` — OSMU 검사에 인스타 채널 포함.
- `progress.json` 의 `pipeline.total` — 15 → 16. 다만 보드는 `STEPS.length` 를
  쓰므로 표시에는 영향이 없다.

## 4. 참고 — 인스타 데이터는 원래부터 쌓이고 있었다

이번 작업의 핵심은 "인스타를 새로 추적하기 시작한 것"이 아니다.
DB에는 이미 **54편의 `osmu.instagram` URL** 이 기록되어 있었고, 콘솔만 그것을
표시하지 않고 있었다. 파이프라인 단계에도, 4채널 지표에도, 미결 매칭에도 없었다.

즉 **수집은 되는데 보이지 않는 데이터**였다. 이제 세 곳 모두에서 보인다.
