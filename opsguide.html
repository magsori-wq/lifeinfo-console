공통 패턴 — 한 문장

판정기가 자기가 안 보는 필드 때문에 멀쩡한 것을 빨간불로 만든다.

같은 계열의 과거 사고:

  • autoflow가 DB에 없는 crosslink 필드를 추측 → 201편 전부 미결
  • index_status의 크롤 필드를 last_crawl로 넘겨짚음 → 175건 전부 "0%" 가짜 결론
  • link_rot 오탐 139건 · agentcheck이 v0의 기록 절을 못 찾아 실패 판정

🔴 왜 이게 치명적인가

지울 수 없는 빨간불은 무시되는 빨간불이 된다.

실측: loopcheck 표에 오탐 3건이 섞여 있던 날, **진짜 보고(seodesc0828)가 48시간

방치**됐다. 이과장이 성공을 보고했는데 관제탑이 안 읽었다. 표가 길어지면 진짜가 묻힌다.

오탐은 성가신 게 아니라 감시망 자체를 죽인다.

3. 오탐을 만들지 않는 5가지 — 판정기를 만들 때

① 스키마를 추측하지 마라 — ls·list(one)로 눈으로 봐라

index_status.json의 posts는 dict다(list 아님). _items()로 읽어 0건이 나왔다.

오탐 감시기를 만들면서 그 함정을 다시 밟았다.

필드명도 같다 — lastCrawl(카멜)이지 last_crawl(스네이크)이 아니다.

② 전건(100%)·영건(0%)이면 발견이 아니라 매칭 버그다

CLAUDE.md 475행에 8일 전부터 문장으로 있었는데 지켜지지 않았다.

→ 2026-08-30에 코드로 집행하게 했다: python -m studio.falsepos

③ 0이 목표인 지표를 "의심"으로 띄우지 마라

미결 0건은 좋은 상태다. 그걸 매번 ⚠️로 띄우면 그 도구 자신이 소음이 된다 —

막으려던 병에 스스로 걸린다. falsepos의 zero_ok 플래그가 그 자리다.

④ 임계값은 한 곳에만 둔다

loopcheck ⓪의 임계가 60초여서 커밋할 때마다 켜졌다 → STALE_RULE_HOURS = 12.

pace 상수가 워크플로와 열흘간 갈라졌던 그 병을 반복하지 않는다.

⑤ 만든 도구가 실제로 잡는지 검증해라

falsepos가 만든 당일 조용히 죽어 있었다 — loopcheck.rows()를 불렀는데 실제

이름은 scan()이었고, 예외를 삼키게 해 둬서 실패해도 아무 말이 없었다.

검증 방법: 일부러 오탐을 넣어 잡히는지 본다.

틀린 필드명        → 🔴 잡음
전건 100%          → 🔴 잡음
영건 + 목표 아님    → 🔴 잡음
영건 + 목표 0      → 조용함   ← 소음 억제까지 확인

4. 미결을 닫는 절차 — 근거를 대고 닫는다

🔴 "오래됐으니 닫는다"로 가면 발행 대기 중인 글을 조용히 잃는다.

순서

1. 그 배치·항목의 실제 내용을 읽는다        (제목만 보지 않는다)
2. 미완 항목마다 지금 상태를 실측한다        (담당 도구로)
3. 이미 해결됐으면 → 근거를 note 에 적고 done
4. 낡았으면(수치·대상이 바뀜) → 그 사실을 note 에 적고 done
5. 하면 안 되는 것이면 → skip + 사유         (열어두면 누군가 실행한다)
6. 살아 있으면 → 담당에 맞는 곳으로 옮긴다   (사장님 몫이면 watch --owner user)
7. 배치가 미완 0건이 되면 그때 닫는다

Blogger가 저장을 받지 않는다.** 편집기엔 들어가는데 라이브는 그대로라

①번 증상과 똑같아 구분이 안 됐다.

7. 경로·스키마를 추측하지 않기 위한 확인 목록

그날 세 번 틀렸다. 다음에 쓸 것:

무엇실제

배포 저장소 레이아웃webapp/* → 배포 저장소의 루트 (webapp/ 하위 아님)

루틴 모델 설정서버(루틴 편집 창)에만 있음. SKILL.md frontmatter에 넣어도 무효

공통 규칙: ls·list(dict)로 먼저 보고 말한다. 문서 표현만 믿지 않는다.
